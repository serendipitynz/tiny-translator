# tiny-translator 設計

PLaMo 3 Translate をローカルで動かす簡易翻訳デスクトップアプリの設計。実装はフェーズごとに別セッションで進めるので、
各セッションが会話の経緯なしにこの文書とタスクから作業を始められるように書く。先行事例と差別化は doc-2 にある。

## 1. この文書が使う語

| 語 | 指すもの |
|---|---|
| 第一優先言語 / 第二優先言語 | 利用者が設定画面で順に並べた出力言語の 1 番目と 2 番目 |
| 翻訳元言語 | アプリが原文から判定した言語、または利用者が翻訳元の選択欄で指定した言語 |
| 優先順位による翻訳先の決定 | 翻訳元言語が第一優先言語なら第二優先言語を、それ以外なら第一優先言語を翻訳先にする規則 |
| 起動時のクリップボード翻訳 | 起動直後にクリップボードがテキストを持つとき、それを原文欄へ入れて翻訳を始める動作 |
| 翻訳エンジン | アプリが子プロセスとして起動し、PLaMo 3 Translate の GGUF を読み込んだ llama-server |
| 自動解放までの時間 | 最後の翻訳が終わってから翻訳エンジンを終了するまでの分数 (設定値) |
| 翻訳エンジンの自動解放 | 自動解放までの時間が過ぎたときに、アプリが翻訳エンジンのプロセスを終了すること |
| 構造保持翻訳 | 原文を形式ごとに解析し、翻訳すべきテキストだけを翻訳して元の構造へ戻す処理 |
| 翻訳単位 | 構造保持翻訳で 1 回のプロンプトとしてモデルへ渡すテキストのまとまり |
| 翻訳履歴 | 1 回の翻訳ごとに保存する原文・訳文・翻訳元言語・翻訳先言語・形式・日時の組 |

## 2. 要求

| # | 要求 | 本書の節 |
|---|---|---|
| R1 | オフラインで動く (モデル取得後はネットワークを使わない) | §4, §10 |
| R2 | 他のアプリ (LM Studio・Ollama など) に依存しない。ランタイムとモデルはアプリが持つ | §4 |
| R3 | 起動時のクリップボード翻訳 | §6.3 |
| R4 | 左に原文、右に訳文の 2 ペイン。それぞれにコピーボタン | §8 |
| R5 | 翻訳元は自動判定を基本とし、指定もできる。翻訳先は優先順位による翻訳先の決定に従う | §6 |
| R6 | メモリ使用を抑え、他のアプリを圧迫しない。小さいモデルの利用は許容 | §5, §7 |
| R7 | 翻訳履歴を参照できる | §9 |
| R8 | Markdown・JSON・HTML の構造を訳文でも保つ | §7 |
| R9 | 見た目は snz-design のトークンと部品仕様に従う | §8 |

対象機: メモリ 16 GB 程度の Apple M1/M2、AMD Ryzen Z1 (内蔵 GPU Radeon 780M / 740M)、VRAM 8 GB 程度の GPU を積んだ Windows PC。

**macOS (Apple Silicon) を主対象にする** (2026-11-06 オーナー判断)。先行アプリ tanakh/plamo-translate-desktop が Windows と Linux を対象にし、
macOS を対象外としているためである (doc-2)。Windows は副対象とし、各フェーズはまず macOS で完了させ、Windows での確認はそのフェーズの最後のタスクで行う。

## 4. 翻訳エンジン

### 4.1 llama-server を子プロセスにする理由

- **プロセスを終了すればメモリを確実に OS へ返せる** (R6)。同じプロセス内に llama.cpp を組み込む形 (`llama-cpp-2` など) では、
  モデルを解放してもアロケーターがメモリを抱えたままになることがあり、確かめにくい。
- llama.cpp の更新を、アプリの再ビルドではなくバイナリの差し替えで取り込める。
- GPU のバックエンドごとにビルドを分けられる。

代わりに、起動待ち (モデルの読み込み) とポートの管理が要る。ポートは 127.0.0.1 の空きポートを起動時に選び、外部から接続させない。

### 4.2 プラットフォーム別のバックエンド

| OS | llama-server のビルド | 備考 |
|---|---|---|
| macOS (Apple Silicon) — 主対象 | Metal | 統合メモリなので、GPU に載せたモデルもシステムメモリを使う |
| Windows (x86_64) — 副対象 | Vulkan | NVIDIA・AMD (Z1 の 780M を含む)・Intel を 1 つのビルドで扱う。CUDA 版は配布サイズが大きいので採らない |

Windows on ARM と Linux は対象外とし、需要が出たら検討する。

### 4.3 プロンプト

PLaMo 3 Translate は PFML3 形式のプロンプトを取る (モデルカード)。例:

```
<|plamo:tag|>dataset<|plamo:msg|>translation<|plamo:tag|>input<|plamo:msg|>{原文}<|plamo:tag|>output<|plamo:key|>lang<|plamo:val|>{翻訳先言語}<|plamo:msg|>
```

- llama-server の `/completion` に、アプリで組み立てたこの文字列を渡す。チャットテンプレート (`chat_template.jinja`) と
  `chat_template_kwargs` の実装差に左右されないためである。
- 停止トークンは `<|plamo:tag|>` と `<|plamo:bos|>`。GGUF の語彙はこの 2 つを生成の終わりを表すトークン (EOG) にしているので、
  llama-server はどちらを生成しても `stop_type: "eos"` で止まる (TASK-1 で確認。§4.5 の実測を参照。通常の翻訳では `<|plamo:tag|>` で止まる)。
  リクエストの `stop` にも 2 つを入れておくが、これは GGUF の設定が変わったときの備えで、現行の GGUF では使われない。
- 先頭の `<|plamo:bos|>` は llama-server が自動で付けるので、アプリが組み立てる文字列には入れない (モデルカード)。
- 訳文はストリーミングで受け、訳文欄へ順に出す。
- 翻訳元言語・文脈 (context)・用語集 (glossary)・日本語の常体と敬体 (form) は PFML3 の属性として渡せる。初版で使うのは翻訳先言語と翻訳元言語だけで、
  文脈は構造保持翻訳の前後の翻訳単位を渡すのに使う (§7.3)。

### 4.4 モデル

| サイズ | GGUF Q4_K_M | 位置付け |
|---|---|---|
| 0.8B | 0.57 GB | 省メモリ。翻訳品質は 2B とほぼ同じ (PFTB で 0.586 と 0.606) |
| 2B | 1.81 GB | **既定** |
| 8B | 5.28 GB | VRAM 8 GB 機の高品質の選択肢。16 GB の Mac では他のアプリを圧迫するので勧めない |

31B は対象外。BF16・FP8・MLX などの形式は llama.cpp で読めないので扱わない。

### 4.5 メモリを抑える方法

- **翻訳エンジンの自動解放**: 自動解放までの時間 (既定 10 分。0 は「解放しない」) が過ぎたら翻訳エンジンを終了する。
  次の翻訳で再び起動し、その間は翻訳ボタンを処理中の表示にする。
- コンテキスト長は既定 8,192 トークンにする (KV キャッシュを抑える)。長い原文は §7 の翻訳単位に分けて送る。
- llama-server の並列数は 1 (`--parallel 1`)。
- 設定画面に、現在の翻訳エンジンの状態 (停止中・読み込み中・待機中) とメモリ使用量の目安を出す。

#### macOS での実測 (TASK-1)

測定機は MacBook Air (M2, メモリ 24 GB, ファンなし)、macOS 26.7.1。llama-server は ggml-org/llama.cpp の GitHub リリースのうち、
安定版 v0.9.0 が指すビルド b12110 (commit `cd959bae9`、ggml 0.29.0) の `llama-b12110-bin-macos-arm64.tar.gz` (Metal 版)。
GGUF は Hugging Face の `pfnet/plamo-3-translate-{0.8b,2b,8b}-GGUF` の Q4_K_M (SHA-256 はリポジトリの値と一致)。
起動の引数はアプリと同じ形の `-c 8192 --parallel 1 --host 127.0.0.1 --port <空きポート>` で、3 サイズとも全レイヤーが GPU に載った。
計測には `scripts/measure_engine.py` を使った。

この節で使う語:

- **読み込み時間**とは、llama-server を起動してから `/health` が 200 を返すまでの秒数を指す。GGUF がページキャッシュに載った状態での値。
- **RSS** は `ps` の値。mmap した GGUF の重みを含む。
- **アクティビティモニタの「メモリ」** は `footprint` の phys_footprint で、mmap した重みを含まない。
- **使用済みメモリ**は OS 全体の値 (アクティビティモニタの「使用済みメモリ」と同じ内訳。`vm_stat` の Anonymous − purgeable + wired + compressor)。
- **冷えた状態**とは、GPU 負荷のない状態で 3 分以上置いた後を指す。

| サイズ | 読み込み時間 | RSS | アクティビティモニタの「メモリ」 | 使用済みメモリの増加 | 生成速度 (冷えた状態) | 1,024 トークン連続生成 | 原文の処理速度 |
|---|---|---|---|---|---|---|---|
| 0.8B | 1.3〜1.7 秒 | 0.76 GB | 0.11〜0.14 GB | +0.86 GB | 140 tok/s | 140 tok/s | 約 1,200 tok/s |
| 2B | 1.4〜1.5 秒 | 2.1 GB | 0.24〜0.26 GB | +2.2 GB | 47 tok/s | 47 tok/s | 約 330 tok/s |
| 8B | 1.8〜3.3 秒 | 5.4 GB | 0.29〜0.32 GB | +5.3〜5.4 GB | 16 tok/s | 3.8 tok/s | 約 110 tok/s |

生成速度は英日・日英の各 4 回 (訳文は 58〜64 トークン) の値で、ばらつきは ±3% 以内。1,024 トークン連続生成は `llama-bench -n 1024` の値。

読み取れること:

- **メモリの実際の消費は RSS で見る。** Metal 版は GGUF を mmap して GPU のバッファにするので、重みはアクティビティモニタの「メモリ」に出ないが、
  使用済みメモリは RSS とほぼ同じだけ増える。§4.5 の設定画面に出す「メモリ使用量の目安」は RSS を使う。
- **16 GB の機械では 2B (既定) は他のアプリを圧迫しない。** 8B は 5.4 GB を占め、ブラウザなどと併用すると足りなくなる (§4.4 の「勧めない」の裏付け)。
- **ファンのない機体では、GPU 負荷を数分続けると熱で生成速度が落ちる。** 8B の 1,024 トークン連続生成は 16 → 3.8 tok/s に落ちた。
  2B も、計測を 10 分ほど続けた後は 47 → 5〜17 tok/s に落ちた。通常の翻訳 (数十〜数百トークン) では冷えた状態の速度が出る。
  長い原文を構造保持翻訳で訳し続ける場合 (§7.3) は、この低下を前提にする。
- **読み込み時間は自動解放 (§4.5) の後の再起動でも問題にならない。** 2B で約 1.5 秒。
  ただし、ダウンロードした直後の最初の 1 回だけ、モデルを読み込む前の初期化に約 10 秒かかった (2 回目以降は 0.06 秒)。原因は未確認 (ダウンロードしたファイルを OS やウイルス対策ソフトが初回に検査するためと推測)。
- 計測中に他のアプリでメモリが足りなくなると (スワップ 14 GB の状態)、2B が 7〜12 tok/s、8B が 3〜4 tok/s に落ち、回ごとのばらつきも大きくなった。
  上の表は LM Studio・Chrome などを終了し、スワップが 4 GB まで減った状態で測った。

llama-server の引数について分かったこと (どれを使うかは翻訳エンジンのタスク (m-2) で決める):

- `--cache-ram` (プロンプトのキャッシュ) の既定は 8,192 MiB で、上限まで RAM を使いうる。R6 のため `--cache-ram 0` か小さい値にすることを検討する。
- 起動時にメモリへ収まるよう引数を調整する処理 (`-fit`、既定で有効) に約 0.9 秒かかる。`-fit off` にすると読み込み時間が 0.8〜1.2 秒 (0.8B・2B) になる。
  ただし、メモリが足りない機械で自動調整が効かなくなる。
- 以前の `--no-mmap` は `--load-mode` (`-lm`) に置き換わっている。`-lm none` で mmap をやめると、重みがアクティビティモニタの「メモリ」にも出るようになるが、
  使用済みメモリと生成速度は変わらなかった。

**まだ測っていないこと**: 16 GB の機械と M1、Z1 (TASK-12)、再起動直後などページキャッシュに GGUF が無い状態の読み込み時間。
先行事例の実測では、2B Q4_K_M を Ryzen 9 9950X の CPU で動かしたとき約 19.5 tok/s だった (doc-2)。

## 5. 起動と終了

- 単一インスタンスにする (`tauri-plugin-single-instance`)。2 回目の起動は既存のウィンドウを前面に出し、起動時のクリップボード翻訳をそのウィンドウで行う。
- ウィンドウの位置と大きさを保存する (`tauri-plugin-window-state`)。
- 起動直後に翻訳エンジンを先に起動しておく (クリップボードが空でも)。読み込みの待ち時間を、利用者が原文を貼るまでの間に隠すため。
- アプリ終了時に翻訳エンジンを必ず終了する。アプリが異常終了して子プロセスが残った場合に備え、起動時に前回の PID を確かめて残っていれば終了する。

## 6. 翻訳の向き

### 6.1 翻訳元言語の判定

翻訳先を決めるには翻訳元言語をアプリ側で知る必要がある。PLaMo 3 Translate は翻訳元言語を省略すると内部で推定するが、その結果を外から取り出せないためである。

- 翻訳元の選択欄が「自動判定」のときは、`whatlang` で判定する。
- 日本語は仮名を含むかで先に判定する (漢字だけの短文を中国語と誤らないため)。
- 判定の確からしさが低いときは、翻訳元言語をプロンプトに入れず (モデルに推定させ)、翻訳先は第一優先言語にする。
- 判定した言語を翻訳元の選択欄の近くに「判定: 英語」の形で出す。

**要確認**: 1〜2 語の短文で whatlang がどれだけ当たるか。m-0 で測る。

### 6.2 優先順位による翻訳先の決定

翻訳先の選択欄の既定は「自動 (優先順位)」。その間は次の規則で翻訳先を決める。

```
翻訳先(翻訳元言語):
    if 翻訳元言語 == 第一優先言語:
        return 第二優先言語
    return 第一優先言語
```

- 既定値は第一優先言語 = 日本語、第二優先言語 = 英語。
- 利用者が翻訳先の選択欄で言語を選んだときは、その言語に固定する。
- 入れ替えボタン (⇅) は、翻訳元と翻訳先の選択欄の値を入れ替え、訳文を原文欄へ移す。

### 6.3 起動時のクリップボード翻訳

- 起動直後 (2 回目の起動を含む) にクリップボードのテキストを読む。空、またはテキスト以外なら何もしない。
- 前回の起動時に翻訳した文字列と同じなら翻訳しない (同じ内容を繰り返し訳さないため)。
- 設定で無効にできる。
- **macOS のクリップボードのプライバシー確認**: 新しい macOS では、アプリがクリップボードを読むときに確認が出ることがある。
  m-0 で実機の挙動を確かめ、確認が出る場合はその旨をこの節に追記する。

## 7. 構造保持翻訳

### 7.1 方式

原文全体をモデルに渡して「構造を保つ」ことを頼む形は採らない。小さいモデルでは記法が崩れることがあるためである。
アプリが原文を解析し、翻訳単位だけをモデルに渡し、訳文を元の位置へ戻す。

| 形式 | 翻訳単位 | 翻訳しないもの |
|---|---|---|
| プレーンテキスト | 空行で区切った段落 | なし |
| Markdown | 段落・見出し・リスト項目・表のセル・引用 | コードブロック、インラインコード、URL、HTML ブロック、front matter |
| JSON | 文字列の値 | キー、数値・真偽値・null。設定で「翻訳しないキー」を指定できる |
| HTML | ブロック要素の中身 (インライン要素を含む) | `script`・`style`・`code`・`pre`、属性値 (ただし `alt`・`title` は翻訳する) |

インライン要素 (Markdown の強調・リンク、HTML の `<a>` など) を含む翻訳単位は、要素を番号付きのタグ (`<a i="2">…</a>` の形) に置き換えてモデルへ渡し、
訳文のタグを元の要素へ戻す。PLaMo 3 Translate はブラウザ翻訳用にタグを保つ学習をしており、先行事例も 0.8B と 2B でタグの順序の入れ替えまで保たれたと報告している (doc-2)。
タグの数や番号が原文と合わない訳文は、タグを外して翻訳し直す。

### 7.2 形式の判定

- 原文欄の上に形式の選択 (自動 / テキスト / Markdown / JSON / HTML) を置く。
- 自動のときは、JSON として読めれば JSON、`<html` か閉じタグを含むブロック要素が多ければ HTML、見出し・リスト・コードフェンスの記法があれば Markdown、どれでもなければテキストとする。
- 判定した形式を原文欄の上に出す。

### 7.3 長い原文

- 翻訳単位を順に翻訳し、直前の翻訳単位の原文と訳文を文脈としてプロンプトに入れる (訳語のぶれを抑える)。
- モデルの学習時の最大長は入力と出力を合わせて 32,768 トークン。1 つの翻訳単位がコンテキスト長に収まらないときは文の境界で分ける。
- 出力が同じ文字列を繰り返し始めたら打ち切り、その翻訳単位を文の単位に分けて訳し直す (先行事例が実装している対策。doc-2)。
- 翻訳中は停止できる。

## 8. 画面

### 8.1 レイアウト

PLaMo 翻訳の画面に倣う。

```
┌ ヘッダー: アプリ名                         [履歴] [設定] ┐
│ [翻訳元の選択欄 ▾]               [翻訳先の選択欄 ▾]       │
│ ┌ 原文 ──── [貼り付け][コピー][クリア] ┐ ┌ 訳文 ──── [コピー] ┐ │
│ │ 複数行入力                         │ │ 読み取り専用        │ │
│ └ 形式: 自動 (Markdown)  判定: 英語 ┘ └────────────────┘ │
│ [⇅]                     [ 翻訳 ] (処理中は「翻訳中…」)      │
└───────────────────────────────────────┘
```

- ウィンドウの幅が狭いときは、原文と訳文を上下に並べる。
- 訳文は翻訳を始めるたびに空にし、ストリーミングで埋める。
- ショートカット: Ctrl/Cmd+Enter で翻訳、Ctrl/Cmd+Shift+C で訳文をコピー。

### 8.2 snz-design の部品との対応

トークンは snz-design のリリース `tokens-v0.1.1` の `snz-tokens.css` を `vendor.mjs copy` で写して使う。写しには手を加えない。

| 画面の要素 | snz-design の部品 |
|---|---|
| 履歴・設定・貼り付け・コピー・クリア・入れ替え | アイコンのみボタン (doc-8 §6.2)。読み上げ用の語を必ず持つ |
| 翻訳元・翻訳先・形式の選択欄 | 入力欄の選択欄 (doc-8 §6.3) |
| 原文と訳文の枠 | パネル (doc-9 §6.3) と複数行入力 (doc-8 §6.3) |
| 翻訳ボタン | ボタンの主操作 (doc-8 §6.1) と処理中の表示 (doc-8 §6.7)。処理中も語を残し、幅を変えない |
| コピーしたことの通知 | 一時的な通知 (doc-9 §6.5) |
| 翻訳履歴の一覧 | 一覧 (doc-9 §6.1) |
| 設定 | モーダル (doc-9 §6.6) と 2 軸の設定画面の実例 (doc-9 §7) |

- **macOS の WKWebView では `select` の枠と面に CSS の指定が反映されない** (snz-design doc-8 §6.3)。自分で描いた枠の内側に `select` を置く。
- IME の変換中は Enter・Escape を操作として受けない (doc-8 §5.6)。

### 8.3 配色

- 配色系統 (標準 / Solarized) と明暗の選択 (Light / Dark / OS 追従) の 2 軸を設定画面で選ぶ (snz-design doc-7 §4)。初期値は標準 + OS 追従。
- ヘッダーに明暗の切り替えボタンは置かない。押すたびに保存値が Light / Dark に変わり、OS 追従の選択を消してしまうためである。
- 配色は最初の描画より前に確定させる (doc-7 §7.1)。保存値を `localStorage` に置き、`index.html` の head 内のスクリプトで `data-color-family` と `data-color-mode` を設定する。
  backlog-atlas は Rust から設定を読み終えるまで標準配色を一瞬表示しており、同じ形は採らない。

### 8.4 初版で置かないもの

- 音声入力 (PLaMo 翻訳の画面のマイク)。オフラインで音声を認識するには別のモデルが要り、R6 と相反する。
- 用語集・文脈の入力欄、常体と敬体の選択。モデルは対応しているので、後のフェーズで検討する。

## 9. 翻訳履歴

- 翻訳が完了するたびに SQLite へ保存する。項目は原文・訳文・翻訳元言語・翻訳先言語・形式・モデル名・日時。
- 途中で停止した翻訳は保存しない。
- 原文と訳文を FTS5 で全文検索する。日本語を検索できるように trigram トークナイザーを使う。
- 履歴の一覧から 1 件を選ぶと、原文・訳文・言語の選択を画面へ戻す。
- 保存件数の上限 (既定 1,000 件) を超えたら古いものから消す。全件削除と 1 件削除の操作を持つ。
- 保存先は OS のアプリデータディレクトリ。
