# tiny-translator 設計

PLaMo 3 Translate をローカルで動かす簡易翻訳デスクトップアプリの設計。実装はフェーズごとに別セッションで進めるので、
各セッションが会話の経緯なしにこの文書とタスクから作業を始められるように書く。先行事例と差別化は doc-2 にある。

## 1. この文書が使う語

| 語 | 指すもの |
|---|---|
| 第一優先言語 / 第二優先言語 | 利用者が設定画面で順に並べた出力言語の 1 番目と 2 番目 |
| 翻訳元言語 | アプリが原文から判定した言語、または利用者が翻訳元の選択欄で指定した言語 |
| 優先順位による翻訳先の決定 | 翻訳元言語が第一優先言語なら第二優先言語を、それ以外なら第一優先言語を翻訳先にする規則 |
| 起動時のクリップボード翻訳 | 起動直後にクリップボードがテキストを持つとき、それを原文欄へ入れて翻訳を始める動作 |
| 翻訳エンジン | アプリが子プロセスとして起動し、PLaMo 3 Translate の GGUF を読み込んだ llama-server |
| 自動解放までの時間 | 最後の翻訳が終わってから翻訳エンジンを終了するまでの分数 (設定値) |
| 翻訳エンジンの自動解放 | 自動解放までの時間が過ぎたときに、アプリが翻訳エンジンのプロセスを終了すること |
| 構造保持翻訳 | 原文を形式ごとに解析し、翻訳すべきテキストだけを翻訳して元の構造へ戻す処理 |
| 翻訳単位 | 構造保持翻訳で 1 回のプロンプトとしてモデルへ渡すテキストのまとまり |
| 翻訳履歴 | 1 回の翻訳ごとに保存する原文・訳文・翻訳元言語・翻訳先言語・形式・日時の組 |

## 4. 翻訳エンジン

### 4.1 llama-server を子プロセスにする理由

- **プロセスを終了すればメモリを確実に OS へ返せる** (R6)。同じプロセス内に llama.cpp を組み込む形 (`llama-cpp-2` など) では、
  モデルを解放してもアロケーターがメモリを抱えたままになることがあり、確かめにくい。
- llama.cpp の更新を、アプリの再ビルドではなくバイナリの差し替えで取り込める。
- GPU のバックエンドごとにビルドを分けられる。

代わりに、起動待ち (モデルの読み込み) とポートの管理が要る。ポートは 127.0.0.1 の空きポートを起動時に選び、外部から接続させない。

### 4.2 プラットフォーム別のバックエンド

| OS | llama-server のビルド | 備考 |
|---|---|---|
| macOS (Apple Silicon) — 主対象 | Metal | 統合メモリなので、GPU に載せたモデルもシステムメモリを使う |
| Windows (x86_64) — 副対象 | Vulkan | NVIDIA・AMD (Z1 の 780M を含む)・Intel を 1 つのビルドで扱う。CUDA 版は配布サイズが大きいので採らない |

Windows on ARM と Linux は対象外とし、需要が出たら検討する。

**sidecar はソースから静的にビルドする** (TASK-8、2026-11-07 オーナー判断)。GitHub リリースの macOS 版 llama-server は 50 KB の本体が
`@loader_path` 経由で dylib を 10 個以上読み込む形で、Tauri の `bundle.externalBin` が同梱する 1 ファイルに収まらないためである。
`scripts/build-llama-server.sh` が TASK-1 と同じ b12110 (commit `cd959bae9`) を `BUILD_SHARED_LIBS=OFF`・`GGML_METAL_EMBED_LIBRARY=ON`・
`LLAMA_CURL=OFF`・`LLAMA_OPENSSL=OFF`・`GGML_NATIVE=OFF` (M1 で動かない命令を使わないため) でビルドし、`src-tauri/binaries/` (追跡しない) へ置く。
できるバイナリは約 23 MB で、OS の外のライブラリをリンクしていない (スクリプトが `otool -L` で確かめる)。

**Windows の Vulkan 版も同じ理由でソースから静的にビルドする** (TASK-12、2026-11-08 オーナー判断)。GitHub リリースの win-vulkan 版は
`llama.dll` と `ggml-*.dll` に分かれている。`scripts/build-llama-server.ps1` が同じ b12110 を `GGML_VULKAN=ON`・`BUILD_SHARED_LIBS=OFF`・
`GGML_NATIVE=OFF` (CPU の命令を AVX2 までにする。Zen 4 の Z1 でビルドしても AVX-512 の無い Zen 3 以前で動くように)・
`GGML_OPENMP=OFF` と `CMAKE_MSVC_RUNTIME_LIBRARY=MultiThreaded` (`vcomp140.dll` と VC++ ランタイムの DLL を読み込まないため)・
`LLAMA_CURL=OFF`・`LLAMA_OPENSSL=OFF` でビルドし、`src-tauri/binaries/llama-server-x86_64-pc-windows-msvc.exe` へ置く。
ビルドには Visual Studio の C++ と Vulkan SDK (シェーダーをコンパイルする `glslc`) が要る。できる exe は約 54 MB で、読み込む DLL は
OS の `KERNEL32`・`ADVAPI32`・`WS2_32` と、GPU ドライバーが入れる Vulkan のローダー `vulkan-1.dll` だけである
(スクリプトが `dumpbin /dependents` で確かめ、それ以外を読み込んでいたら失敗する)。

### 4.3 プロンプト

PLaMo 3 Translate は PFML3 形式のプロンプトを取る (モデルカード)。例:

```
<|plamo:tag|>dataset<|plamo:msg|>translation<|plamo:tag|>input<|plamo:msg|>{原文}<|plamo:tag|>output<|plamo:key|>lang<|plamo:val|>{翻訳先言語}<|plamo:msg|>
```

- llama-server の `/completion` に、アプリで組み立てたこの文字列を渡す。チャットテンプレート (`chat_template.jinja`) と
  `chat_template_kwargs` の実装差に左右されないためである。
- 停止トークンは `<|plamo:tag|>` と `<|plamo:bos|>`。GGUF の語彙はこの 2 つを生成の終わりを表すトークン (EOG) にしているので、
  llama-server はどちらを生成しても `stop_type: "eos"` で止まる (TASK-1 で確認。§4.5 の実測を参照。通常の翻訳では `<|plamo:tag|>` で止まる)。
  リクエストの `stop` にも 2 つを入れておくが、これは GGUF の設定が変わったときの備えで、現行の GGUF では使われない。
- 先頭の `<|plamo:bos|>` は llama-server が自動で付けるので、アプリが組み立てる文字列には入れない (モデルカード)。
- 訳文はストリーミングで受け、訳文欄へ順に出す。要求は Rust 側から出し、訳文の断片を Tauri の Channel で画面へ渡す。
  翻訳エンジンのポートと API キー (§4.5) を WebView へ出さないためである (TASK-9)。
- `temperature` は 0 にする (TASK-1 の計測と同じ)。`n_predict` は指定せず、長い訳文を途中で切らない。
- 翻訳中は停止できる。停止は要求の接続を閉じて行い、llama-server は切断で生成を取り消して次の要求をすぐ受け付ける
  (TASK-9 の実測: 2B で生成を 1.5 秒で止めた直後の次の翻訳が 0.26 秒で返った)。新しい翻訳を始めると、前の翻訳は止める。
- 翻訳元言語・文脈 (context)・用語集 (glossary)・日本語の常体と敬体 (form) は PFML3 の属性として渡せる。初版で使うのは翻訳先言語と翻訳元言語だけ。
- 直前の翻訳単位の原文と訳文 (§7.3) は context に入れず、公式の `chat_template.jinja` が前の対訳を渡す形で渡す (TASK-13)。
  翻訳する原文の `input` の前に、前の原文の `input` と訳文の `output` を置く (属性は翻訳する原文のものと同じ)。
  context は自由な参考テキストの欄で、入れても原文と訳文の区別がモデルに伝わらないためである。

  ```
  <|plamo:tag|>dataset<|plamo:msg|>translation<|plamo:tag|>input<|plamo:msg|>{前の原文}<|plamo:tag|>output<|plamo:key|>lang<|plamo:val|>{翻訳先言語}<|plamo:msg|>{前の訳文}<|plamo:tag|>input<|plamo:msg|>{原文}<|plamo:tag|>output<|plamo:key|>lang<|plamo:val|>{翻訳先言語}<|plamo:msg|>
  ```

### 4.4 モデル

| サイズ | GGUF Q4_K_M | 位置付け |
|---|---|---|
| 0.8B | 0.57 GB | 省メモリ。翻訳品質は 2B とほぼ同じ (PFTB で 0.586 と 0.606) |
| 2B | 1.81 GB | **既定** |
| 8B | 5.28 GB | VRAM 8 GB 機の高品質の選択肢。16 GB の Mac では他のアプリを圧迫するので勧めない |

31B は対象外。BF16・FP8・MLX などの形式は llama.cpp で読めないので扱わない。

### 4.5 メモリを抑える方法

- **翻訳エンジンの自動解放**: 自動解放までの時間 (既定 10 分。0 は「解放しない」) が過ぎたら翻訳エンジンを終了する。
  次の翻訳で再び起動し、その間は翻訳ボタンを処理中の表示にする。
- コンテキスト長は既定 8,192 トークンにする (KV キャッシュを抑える)。長い原文は §7 の翻訳単位に分けて送る。
- llama-server の並列数は 1 (`--parallel 1`)。
- 設定画面に、現在の翻訳エンジンの状態 (停止中・読み込み中・待機中) とメモリ使用量の目安を出す。

#### macOS での実測 (TASK-1)

測定機は MacBook Air (M2, メモリ 24 GB, ファンなし)、macOS 26.7.1。llama-server は ggml-org/llama.cpp の GitHub リリースのうち、
安定版 v0.9.0 が指すビルド b12110 (commit `cd959bae9`、ggml 0.29.0) の `llama-b12110-bin-macos-arm64.tar.gz` (Metal 版)。
GGUF は Hugging Face の `pfnet/plamo-3-translate-{0.8b,2b,8b}-GGUF` の Q4_K_M (SHA-256 はリポジトリの値と一致)。
起動の引数はアプリと同じ形の `-c 8192 --parallel 1 --host 127.0.0.1 --port <空きポート>` で、3 サイズとも全レイヤーが GPU に載った。
計測には `scripts/measure_engine.py` を使った。

この節で使う語:

- **読み込み時間**とは、llama-server を起動してから `/health` が 200 を返すまでの秒数を指す。GGUF がページキャッシュに載った状態での値。
- **RSS** は `ps` の値。mmap した GGUF の重みを含む。
- **アクティビティモニタの「メモリ」** は `footprint` の phys_footprint で、mmap した重みを含まない。
- **使用済みメモリ**は OS 全体の値 (アクティビティモニタの「使用済みメモリ」と同じ内訳。`vm_stat` の Anonymous − purgeable + wired + compressor)。
- **冷えた状態**とは、GPU 負荷のない状態で 3 分以上置いた後を指す。

| サイズ | 読み込み時間 | RSS | アクティビティモニタの「メモリ」 | 使用済みメモリの増加 | 生成速度 (冷えた状態) | 1,024 トークン連続生成 | 原文の処理速度 |
|---|---|---|---|---|---|---|---|
| 0.8B | 1.3〜1.7 秒 | 0.76 GB | 0.11〜0.14 GB | +0.86 GB | 140 tok/s | 140 tok/s | 約 1,200 tok/s |
| 2B | 1.4〜1.5 秒 | 2.1 GB | 0.24〜0.26 GB | +2.2 GB | 47 tok/s | 47 tok/s | 約 330 tok/s |
| 8B | 1.8〜3.3 秒 | 5.4 GB | 0.29〜0.32 GB | +5.3〜5.4 GB | 16 tok/s | 3.8 tok/s | 約 110 tok/s |

生成速度は英日・日英の各 4 回 (訳文は 58〜64 トークン) の値で、ばらつきは ±3% 以内。1,024 トークン連続生成は `llama-bench -n 1024` の値。

読み取れること:

- **メモリの実際の消費は RSS で見る。** Metal 版は GGUF を mmap して GPU のバッファにするので、重みはアクティビティモニタの「メモリ」に出ないが、
  使用済みメモリは RSS とほぼ同じだけ増える。§4.5 の設定画面に出す「メモリ使用量の目安」は RSS を使う。
- **16 GB の機械では 2B (既定) は他のアプリを圧迫しない。** 8B は 5.4 GB を占め、ブラウザなどと併用すると足りなくなる (§4.4 の「勧めない」の裏付け)。
- **ファンのない機体では、GPU 負荷を数分続けると熱で生成速度が落ちる。** 8B の 1,024 トークン連続生成は 16 → 3.8 tok/s に落ちた。
  2B も、計測を 10 分ほど続けた後は 47 → 5〜17 tok/s に落ちた。通常の翻訳 (数十〜数百トークン) では冷えた状態の速度が出る。
  長い原文を構造保持翻訳で訳し続ける場合 (§7.3) は、この低下を前提にする。
- **読み込み時間は自動解放 (§4.5) の後の再起動でも問題にならない。** 2B で約 1.5 秒。
  ただし、ダウンロードした直後の最初の 1 回だけ、モデルを読み込む前の初期化に約 10 秒かかった (2 回目以降は 0.06 秒)。原因は未確認 (ダウンロードしたファイルを OS やウイルス対策ソフトが初回に検査するためと推測)。
- 計測中に他のアプリでメモリが足りなくなると (スワップ 14 GB の状態)、2B が 7〜12 tok/s、8B が 3〜4 tok/s に落ち、回ごとのばらつきも大きくなった。
  上の表は LM Studio・Chrome などを終了し、スワップが 4 GB まで減った状態で測った。

llama-server の引数について分かったこと (どれを使うかは下の「アプリが使う引数」に書いた):

- `--cache-ram` (プロンプトのキャッシュ) の既定は 8,192 MiB で、上限まで RAM を使いうる。R6 のため `--cache-ram 0` か小さい値にすることを検討する。
- 起動時にメモリへ収まるよう引数を調整する処理 (`-fit`、既定で有効) に約 0.9 秒かかる。`-fit off` にすると読み込み時間が 0.8〜1.2 秒 (0.8B・2B) になる。
  ただし、メモリが足りない機械で自動調整が効かなくなる。
- 以前の `--no-mmap` は `--load-mode` (`-lm`) に置き換わっている。`-lm none` で mmap をやめると、重みがアクティビティモニタの「メモリ」にも出るようになるが、
  使用済みメモリと生成速度は変わらなかった。

#### Windows での実測 (TASK-12)

llama-server は §4.2 の静的ビルド (b12110 の Vulkan 版)。GGUF は macOS と同じ Q4_K_M (SHA-256 はリポジトリの値と一致)。起動の引数はアプリと同じ
`-c 8192 --parallel 1 --host 127.0.0.1 --port <空きポート> --cache-ram 0 --no-webui` で、`scripts/measure_engine.py` (Windows の分岐を TASK-12 で足した) で測った。
1 回の起動につき英日・日英を各 2 回送り、起動を 3 回繰り返した。他のアプリは終了し、AC 電源につないで測った。

| 測定機 | CPU / GPU | メモリ | OS とドライバー | 設定 |
|---|---|---|---|---|
| GPU 機 | Ryzen 7 5800X / GeForce RTX 5060 Ti (VRAM 16 GB) | 48 GB | Windows 11 (10.0.26200)、NVIDIA 32.0.16.1088 | |
| ROG Ally | Ryzen Z1 Extreme / Radeon 780M (内蔵) | 16 GB (うち 4 GB を GPU に割り当て、Windows から見えるのは 12.6 GB) | Windows 11 (10.0.26200)、AMD 32.0.12011.7001 (2024-11-15) | Armoury Crate の動作モードは「パフォーマンス」、GPU に割り当てるメモリ (UMA) は 4 GB |

この節で使う語 (読み込み時間は macOS の節と同じ):

- **ワーキングセット**は、プロセスが今 RAM に置いているページの量。mmap した GGUF のページを含む。
- **プライベートワーキングセット**は、ワーキングセットのうち他のプロセスと共有しない分で、タスクマネージャーの「メモリ」の列の値。
- **専用 GPU メモリ・共有 GPU メモリ**は、タスクマネージャーの「詳細」の同名の列の値 (プロセスごと)。専用は GPU 自身のメモリで、
  GPU 機では VRAM、Ally では UMA の設定で GPU に割り当てた RAM (Windows からは見えない) を指す。共有は、Windows が見ている RAM のうち GPU が使う分。
- **利用可能メモリの減少**は、OS 全体の利用可能な物理メモリ (タスクマネージャーの「利用可能」) が、読み込みの前から読み込み後までに減った量。

| 測定機 | サイズ | 読み込み時間 | ワーキングセット | プライベートワーキングセット | 専用 GPU メモリ | 共有 GPU メモリ | 利用可能メモリの減少 | 生成速度 | 原文の処理速度 |
|---|---|---|---|---|---|---|---|---|---|
| GPU 機 | 0.8B | 2.3〜2.6 秒 | 0.81 GB | 0.30 GB | 0.58 GB | 0.18 GB | 0.75〜0.80 GB | 約 465 tok/s | 約 5,300 tok/s |
| GPU 機 | 2B | 2.8〜3.0 秒 | 2.1 GB | 0.40〜0.43 GB | 1.93 GB | 0.28 GB | 2.1 GB | 約 158 tok/s | 約 2,100 tok/s |
| ROG Ally | 0.8B | 2.4〜2.8 秒 | 0.33 GB | 0.31 GB | 0.60 GB | 0.16 GB | 0.33〜0.38 GB | 約 120 tok/s | 約 1,250 tok/s |
| ROG Ally | 2B | 2.8〜4.4 秒 | 0.61 GB | 0.58 GB | 1.74 GB | 0.44 GB | 0.59〜0.73 GB | 約 39 tok/s | 約 320 tok/s |

生成速度は、起動ごとの最初の要求を除いた値 (訳文は 59〜64 トークン) で、ばらつきは ±3% 以内。Ally は既定の引数で 2 回、`-lm none` で 1 回、
同じ計測を続けて行い (計 30 分ほど)、熱で遅くなることはなかった。ファンが強く回ることはなかった。終了後は 3 秒以内に、両機とも利用可能メモリと GPU 全体の専用メモリが
読み込み前の値 (±0.1 GB) に戻った。訳文はどの回も `stop_type: "eos"` で止まった (macOS と同じ)。Ally の 2B の読み込み時間は、
計測ごとの最初の起動が 3.7〜4.4 秒、2 回目以降が 2.8〜3.3 秒だった。

読み取れること:

- **GPU 機では、重みが VRAM と RAM の両方を使う。** 2B の重みは専用 GPU メモリ (1.93 GB) に載るが、mmap した GGUF のページがワーキングセットに
  残り、利用可能メモリも 2.1 GB 減る。タスクマネージャーの「メモリ」(プライベートワーキングセット) には出ない。
- **GPU 機で `-lm none` にすると、RAM の消費が重みの分だけ減る。** 同じ機械で `-lm none` を足して測ると (各 2 回)、利用可能メモリの減少は
  0.8B で 0.29〜0.32 GB、2B で 0.39〜0.40 GB、読み込み時間は 2.0 秒と 2.25〜2.28 秒になり、生成速度は変わらなかった。
  Ally では `-lm none` を足しても (各 3 回) どの値も変わらなかった。macOS でも変わらなかったので「アプリが使う引数」では `-lm` を
  既定のままにしたが、GPU 機の Windows では引数を変える根拠になる (採るかどうかは未決定)。
- **Z1 では、重みは UMA で GPU に割り当てた 4 GB に載り、Windows の RAM はほとんど使わない。** 2B の重みは専用 GPU メモリ (1.74 GB) に載り、
  利用可能メモリの減少は 0.6〜0.7 GB だった。ただし Ally は他のアプリを終了した状態でも、読み込み前の利用可能メモリが 2.6 GB しかなかった
  (Windows から見える 12.6 GB のうち)。2B は収まったが、余裕は少ない。8B (5.28 GB) は UMA 4 GB の専用メモリに収まらず、測っていない。
  llama-server は GPU のメモリを 9.8 GB と見ている (専用 4 GB と共有の一部) ので、専用に収まらない分は共有、つまり Windows の RAM を使うと推測する。
- **Z1 の速度は M2 より 1〜2 割遅い。** 0.8B が約 120 tok/s (M2 は 140)、2B が約 39 tok/s (M2 は 47)。通常の翻訳 (数十〜数百トークン) では 2B でも待たされない。
  ドライバーは 2024 年 11 月のもので、新しいドライバーでの値は測っていない。
- **exe を置いた直後の最初の起動だけ遅い。** Ally へコピーした直後の最初の起動では読み込みに 5.8 秒、最初の翻訳の原文の処理 (76 トークン) に 0.9 秒かかった
  (2 回目以降は 2.4〜2.8 秒と 0.1 秒)。GPU 機でビルドした直後の最初の起動では読み込みに 7.0 秒、最初の翻訳の原文の処理 (76 トークン) に 7.1 秒かかった
  (LM Studio が 11.7 GB を使っていた状態で、表の値には入れていない)。インストーラーで入れたアプリの最初の起動でも、読み込みに 7.6 秒、
  最初の翻訳の原文の処理 (41 トークン) に 3.7 秒かかった。同じ exe の 2 回目以降の起動では、自動解放の後の再起動を含めて読み込みが 2〜3 秒、
  最初の翻訳も通常の速さだった。原因は確かめていない (GPU ドライバーが exe ごとにシェーダーのキャッシュを作るためと推測。ウイルス対策の初回の検査かもしれない)。

#### アプリが使う引数 (TASK-8)

`-m <GGUF> -c 8192 --parallel 1 --host 127.0.0.1 --port <空きポート> --cache-ram 0 --no-webui` (2026-11-07 オーナー判断)。

- `--cache-ram 0`: プロンプトのキャッシュに RAM を使わない (R6)。翻訳ごとに原文が違い、長い共通部分を再利用できる場面が少ないため。
- `--no-webui`: llama-server がブラウザ向けに出す画面を出さない。翻訳エンジンはアプリ専用である。
- API キー (TASK-9): 起動のたびに OS の乱数源から 32 バイトを取って 16 進にしたキーを作り、`--api-key` と同じ設定を環境変数 `LLAMA_API_KEY` で渡す。
  翻訳の要求は `Authorization: Bearer <キー>` を付け、キーの無い要求 (同じ機械のブラウザで開いたページからの要求など) は 401 になる。
  引数ではなく環境変数にするのは、引数は同じ機械の他の利用者も `ps` で読めるが、環境変数は同じ利用者にしか読めないためである。
  `/health` はキー無しでも答えるので、読み込みの待ちはそのまま使える。
- `-fit` は既定 (有効) のままにする。約 0.9 秒かかるが、`-fit off` にするとメモリの足りない機械で自動調整が効かなくなる。
- `-lm` は既定 (mmap) のままにする。`-lm none` にしても使用済みメモリと生成速度は変わらなかった (上の実測)。
- llama-server の出力は、アプリのログディレクトリ (macOS では `~/Library/Logs/com.serendipitynz.tiny-translator/`、
  Windows では `%LOCALAPPDATA%\com.serendipitynz.tiny-translator\logs\`) の `llama-server.log` に起動のたびに書き直す。
- 読み込み中に llama-server がすぐ終了したときは、新しい空きポートで起動し直す (1 回の起動につき 3 回まで)。空きポートを選んで手放した直後は、
  macOS がそのポートを短い間 (10 ms 以内) 使用中のままにすることがあり、llama-server がポートを取れずに終了するためである (TASK-8 のテストで観測)。
- 読み込みの待ちは 180 秒で打ち切る。スワップが 13 GB ある状態では、2B の読み込みに 3〜30 秒かかった (リリース版と静的ビルドで同じ。TASK-8)。

**まだ測っていないこと**: 16 GB の機械と M1、再起動直後などページキャッシュに GGUF が無い状態の読み込み時間。
先行事例の実測では、2B Q4_K_M を Ryzen 9 9950X の CPU で動かしたとき約 19.5 tok/s だった (doc-2)。

## 5. 起動と終了

- 単一インスタンスにする (`tauri-plugin-single-instance`)。2 回目の起動は既存のウィンドウを前面に出し、起動時のクリップボード翻訳をそのウィンドウで行う。
  macOS では、動いているアプリを Finder・Dock・Spotlight から開き直しても 2 つ目のプロセスは起動せず、動いているアプリに再オープン
  (`RunEvent::Reopen`) が届くだけなので、これも 2 回目の起動として扱う (TASK-11)。Dock のアイコンを押したときも同じ扱いになる。
- ウィンドウの位置と大きさ (と最大化の有無) を保存する (`tauri-plugin-window-state`)。
- 起動直後に翻訳エンジンを先に起動しておく (クリップボードが空でも)。読み込みの待ち時間を、利用者が原文を貼るまでの間に隠すため。
- アプリ終了時に翻訳エンジンを必ず終了する。アプリが異常終了して子プロセスが残った場合に備え、起動時に前回の PID を確かめて残っていれば終了する。
  PID はアプリデータディレクトリの `engine.pid` に置く。終了するのは、その PID のプロセスがアプリの sidecar と同じパスで起動されたものであるときだけにする
  (PID が別のプロセスに使い回されていた場合、たとえば LM Studio の llama-server を止めないため)。
- 自動解放までの時間は、翻訳エンジンが読み込みを終えた時点と、翻訳が終わるたびに数え始める。翻訳中は数えない。

## 6. 翻訳の向き

### 6.1 翻訳元言語の判定

翻訳先を決めるには翻訳元言語をアプリ側で知る必要がある。PLaMo 3 Translate は翻訳元言語を省略すると内部で推定するが、その結果を外から取り出せないためである。

翻訳元の選択欄が「自動判定」のときは、次の規則で翻訳元言語を決める。

```
翻訳元言語(原文):
    if 原文が仮名を含む:
        return 日本語
    結果 = whatlang で判定(原文)
    if 結果が無い or 結果の確からしさ < 0.5:
        return 判定なし
    return 結果の言語
```

- **確からしさ**とは、whatlang の `Info::confidence()` が返す 0.0〜1.0 の値を指す。
- **判定なし**とは、アプリが翻訳元言語を決めない状態を指す。このときは翻訳元言語をプロンプトに入れず (モデルに推定させ)、翻訳先は第一優先言語にする。
- 仮名は平仮名と片仮名 (半角を含む) で、中黒 (U+30FB) は数えない。中黒は約物で、日本語の資料から写した中国語の原文にも現れるためである。
  whatlang も中黒を片仮名として数え、仮名が 5% 以上ある漢字の原文を日本語とするので、whatlang へ渡す前に中黒を空白に置き換える
  (TASK-10。`北京・上海之间的高速铁路` が置き換えなしでは日本語と判定された)。
- whatlang は簡体字と繁体字を見分けないので、中国語と判定した原文は翻訳元言語をプロンプトに入れず、どちらの中国語かはモデルに推定させる (TASK-10)。
  優先順位による翻訳先の決定 (§6.2) では、中国語 (簡体字) と中国語 (繁体字) のどちらの優先言語とも一致するとみなす。
- whatlang が判定しても PLaMo 3 Translate が扱わない言語 (ポルトガル語・トルコ語・ウクライナ語など) は判定なしにする (TASK-10)。
- 判定した言語を原文欄の下 (§8.1) に「判定: 英語」の形で出す。中国語は「判定: 中国語」、判定なしは「判定: 不明」と出す (2026-11-07 オーナー判断)。
  原文が空のときと、翻訳元の選択欄で言語を指定しているときは出さない。判定は原文の入力が 200 ms 止まったときと、翻訳を始めるときに行う。
- 漢字だけの原文 (仮名もハングルも含まず、主な文字種が漢字の原文) は、日本語でも中国語と判定される。この誤りは受け入れ、
  利用者が翻訳元の選択欄で日本語を選び直す (2026-11-06 オーナー判断)。理由は下の実測を参照。

#### whatlang の短文での判定 (TASK-2)

whatlang 0.18.0 で、測定のために書いた 132 件の短文を上の規則で判定した。計測には `scripts/measure_langdetect` を使い、
原文は同じディレクトリの `samples.tsv` にある。「1 文」には `Not found` のような 2〜3 語の句を含む。
TASK-10 でアプリの判定 (`src-tauri/src/language.rs`) に同じ 132 件を通し、翻訳先が正しい件数が 113 件で一致することを確かめた。

表の値は「正しい / 判定なし / 誤り」の件数。

| 原文 | 1 語 | 1 文 | 段落 |
|---|---|---|---|
| 日本語 (仮名を含む) | 8 / 0 / 0 | 6 / 0 / 0 | 2 / 0 / 0 |
| 漢字だけの日本語 (`東京駅`、`本日休業` など) | 0 / 0 / 10 | 0 / 0 / 8 | — |
| 英字混じりの日本語 (`React の useEffect が 2 回呼ばれる` など) | — | 6 / 0 / 0 | — |
| 英語 | 0 / 10 / 0 | 8 / 12 / 0 | 2 / 0 / 0 |
| 漢字や仮名を含む英語 (`Please check the 設定 screen.` など) | — | 1 / 1 / 1 | — |
| フランス語・ドイツ語・スペイン語 | — | 3 / 6 / 0 | — |
| 中国語 (簡体字) | 8 / 0 / 0 | 6 / 0 / 0 | 2 / 0 / 0 |
| 中国語 (繁体字) | 8 / 0 / 0 | 6 / 0 / 0 | 2 / 0 / 0 |
| 韓国語 | 8 / 0 / 0 | 6 / 0 / 0 | 2 / 0 / 0 |

読み取れること:

- **中国語・韓国語・仮名を含む日本語は、1 語でもすべて当たる。** whatlang はこれらを文字の出現頻度 (trigram) ではなく文字種で判定し、
  確からしさは常に 1.0 になる。ハングルなら韓国語、漢字が主なら仮名の割合で日本語か中国語を決める。
- **簡体字と繁体字は見分けない。** whatlang はどちらも同じ言語 (`Cmn`) として返す。
- **漢字だけの日本語は 18 件すべてが中国語 (確からしさ 1.0) と判定された。** 仮名が無いので仮名による判定は効かず、確からしさが 1.0 なので閾値でも除けない。
  既定の優先順位 (日本語・英語) では翻訳先が日本語になり、訳文がほぼ原文のまま返る。簡体字だけにある字 (们・这・谢 など) を含むかで中国語を確定し、
  残りを日本語と扱う方法は、中国語の短文を誤る範囲を測っていないので採らなかった。
- **仮名による判定が効くのは英字混じりの日本語である。** ラテン文字が仮名より多い原文を、whatlang はルーマニア語やスロバキア語などと判定した (whatlang だけでは 6 件中 1 件が正しい)。
  代わりに、日本語の語を引用した英語 (`The word 締め切り means deadline.`) も日本語と判定される。
- **英語の 1 語は 10 語すべてが他の言語 (デンマーク語・フランス語など) と判定された。** 確からしさは 0.00〜0.24。
  1 文では、誤った判定の確からしさは最大 0.27 (`The store opens at ten in the morning.` をオランダ語)、正しい判定は 0.04〜1.00 に散らばった。
- **閾値を 0.5 にした** (2026-11-06 オーナー判断)。英語・フランス語・ドイツ語・スペイン語の 41 件で whatlang の誤りがすべて判定なしになり、誤った判定の最大 0.27 に対してほぼ 2 倍の余裕がある。
  0.3 でも誤りは 0 件だが、余裕がほとんど無い。whatlang 自身の基準 (`is_reliable()` の 0.9 超え) では、英語 32 件のうち英語と決まるのが 6 件に減る。
- **閾値が効くのは、whatlang が文字種だけで言語を決められない文字 (ラテン文字・キリル文字など) の原文である。**
  既定の優先順位では、ラテン文字の原文が判定なしになっても翻訳先は日本語のままで変わらない (閾値を 0.0〜1.0 のどれにしても、翻訳先が正しいのは 132 件中 113 件)。
  閾値で変わるのは、プロンプトに翻訳元言語が入るかと、画面の「判定:」の表示である。翻訳先を誤った 19 件は、漢字だけの日本語 18 件と、日本語の語を引用した英語 1 件。
- 第一優先言語をラテン文字の言語 (英語など) にした利用者では、その言語の短文が判定なしになると翻訳先も第一優先言語になり、訳されない。
  この場合は翻訳先の選択欄で言語を選ぶ必要がある。

### 6.2 優先順位による翻訳先の決定

翻訳先の選択欄の既定は「自動 (優先順位)」。その間は次の規則で翻訳先を決める。

```
翻訳先(翻訳元言語):
    if 翻訳元言語 == 第一優先言語:
        return 第二優先言語
    return 第一優先言語
```

- 既定値は第一優先言語 = 日本語、第二優先言語 = 英語。設定画面 (TASK-21) ができるまでは既定値に固定する。
- 利用者が翻訳先の選択欄で言語を選んだときは、その言語に固定する。
- 入れ替えボタン (⇅) は、翻訳元と翻訳先の選択欄の値をそのまま入れ替え (「自動判定」と「自動 (優先順位)」は互いに入れ替わる)、
  訳文を原文欄へ、原文を訳文欄へ移す (2026-11-07 オーナー判断)。翻訳元が自動判定で翻訳先が言語の指定のときは、
  入れ替えた後の翻訳先は優先順位で決まり、入れ替える前に判定した言語にはならない。翻訳中は押せない。

### 6.3 起動時のクリップボード翻訳

- 起動直後 (2 回目の起動を含む) にクリップボードのテキストを読む。空、またはテキスト以外なら何もしない。
- 前回の起動時に翻訳した文字列と同じなら翻訳しない (同じ内容を繰り返し訳さないため)。比べるために、文字列そのものではなくハッシュを
  アプリデータディレクトリの `launch-clipboard` に置く。クリップボードがパスワードなどを持っていても、ディスクに残さないためである (TASK-11)。
- 設定で無効にできる。
- **macOS では、読んでも確認が出ないときだけ読む** (2026-11-06 オーナー判断)。読む前に `NSPasteboard` の `accessBehavior` を調べ、
  `AlwaysAllow` のときだけ読む。`Default`・`Ask`・`AlwaysDeny` のときは読まず、原文欄が空のときの表示で、システム設定の
  「ほかのアプリからのペースト」でこのアプリを許可すれば起動時に翻訳できることと、Cmd+V で貼り付けられることを伝える。
  確認が出る状態で読むと、確認の「Allow Paste」はその 1 回だけの許可なので、起動のたびに利用者の操作が 1 回増えるためである。
  `accessBehavior` を調べるだけでは確認は出ない。`accessBehavior` が無い macOS 15.4 より前は確認の仕組みも無いので、`AlwaysAllow` と同じに扱う。
  Windows には `accessBehavior` に当たる判定が無いので、常に読む。
- **原文欄の [貼り付け] ボタン (§8.1) は、`accessBehavior` を調べずに常に読む** (2026-11-07 オーナー判断)。プログラムからの読み取りなので、
  `Default`・`Ask` では押すたびに確認が出る (下の実測) が、利用者が自分で求めた読み取りである。`AlwaysDeny` では、Apple の説明では確認を
  出さずに読み取りが拒まれる (試していない)。読めなかったときは「クリップボードに貼り付けられる文字列がありません」と伝える。
  ボタンは原文欄を置き換えるだけで、翻訳は始めない (2026-11-07 オーナー判断)。言語を選び直したり原文を直したりしてから訳せるようにするため。
- **初めて使うときの許可の道筋は [貼り付け] ボタンが担い、案内は `Default` と `Ask` で分けない** (2026-11-07 オーナー判断)。
  `accessBehavior` についての Apple のヘッダーの説明では、システム設定で変えられるのは過去に確認を出したアプリだけで、確認を一度も出していない
  `Default` のアプリは一覧に並ばない (実機の一覧では確かめていない)。Cmd+V は確認を出さないので、一覧に並べる操作にならない。
  そこで原文欄が空のときの案内は、システム設定で許可すれば起動時に翻訳できること、一覧に無いときは先に [貼り付け] ボタンを一度押して確認に
  答えると並ぶこと、Cmd+V で貼り付けられることを、`Default` と `Ask` のどちらにも同じ文で伝える。開発者プレビューを有効にした macOS 26.7.1 で、
  起動時に読まずにこの案内が出て、確認も出ないことを確かめた (TASK-11)。

#### macOS で読むときの確認 (TASK-3)

macOS 26.7.1 (MacBook Air M2) で、tauri-plugin-clipboard-manager 2.5.0 の Rust 側 `read_text` を起動処理 (`setup`) から呼んで確かめた。
確認アプリは `scripts/clipboard_probe` にあり、読み取りの結果と `accessBehavior` をログに残す。原文は `pbcopy` で別のプロセスから置いた。

| 状態 | 起動時の読み取り | `accessBehavior` |
|---|---|---|
| 既定 (何も設定しない) | 確認なしで読める | `AlwaysAllow` |
| 開発者プレビュー (`EnablePasteboardPrivacyDeveloperPreview`) を有効にし、未応答 | 確認が出る。応答するまで `read_text` が返らない (今回は約 24 秒) | `Default` |
| 上の確認で「Allow Paste」を押した後に再起動 | 再び確認が出る | `Ask` |
| システム設定の「ほかのアプリからのペースト」で「許可」にした後に再起動 | 確認なしで読める (36 ms) | `AlwaysAllow` |

読み取れること:

- **現行の macOS 26 では確認は出ない。** 確認は Apple が予告している変更で、macOS 26 では開発者プレビューを有効にしたときだけ動く。
- **確認を出さずに済む許可は、システム設定でだけ保存できる。** 確認の「Allow Paste」は 1 回だけで、`accessBehavior` が `Ask` になり次の起動でまた確認が出る。
  システム設定の「ほかのアプリからのペースト」には、確認を一度出したアプリが `Ask` の状態で並び、そこで「許可」を選ぶと以後は出ない。
- **プログラムから読む限り、確認を出さない読み方は無い。** JS コマンド (`plugin:clipboard-manager|read_text`) をボタンから呼んでも確認が出た。
  Apple の説明では、macOS 15.4 で入った `detect` 系の API は URL や数字などの種類を確認なしで調べられるが、テキストそのものは返さない (試していない)。
- **利用者の貼り付け (Cmd+V) は確認を出さない。** `AlwaysAllow` では確認なしで貼り付けられた。`Ask` では確認は出なかったが、
  Edit メニューの Paste の処理の中でアプリが応答しなくなった (1 回だけの観測で、再現は確かめていない)。

### 6.4 選択欄の言語

翻訳元と翻訳先の選択欄には、PLaMo 3 Translate が扱う 53 言語を並べる (2026-11-07 オーナー判断)。日本語・英語・中国語 (簡体字)・

## 7. 構造保持翻訳

### 7.1 方式

原文全体をモデルに渡して「構造を保つ」ことを頼む形は採らない。小さいモデルでは記法が崩れることがあるためである。
アプリが原文を解析し、翻訳単位だけをモデルに渡し、訳文を元の位置へ戻す。

| 形式 | 翻訳単位 | 翻訳しないもの |
|---|---|---|
| プレーンテキスト | 空行で区切った段落 | なし |
| Markdown | 段落・見出し・リスト項目・表のセル・引用 | コードブロック、インラインコード、URL、HTML ブロック、front matter |
| JSON | 文字列の値 | キー、数値・真偽値・null。設定で「翻訳しないキー」を指定できる |
| HTML | ブロック要素の中身 (インライン要素を含む) | `script`・`style`・`code`・`pre`、属性値 (ただし `alt`・`title` は翻訳する) |

インライン要素 (Markdown の強調・リンク、HTML の `<a>` など) を含む翻訳単位は、要素を番号付きのタグ (`<a i="2">…</a>` の形) に置き換えてモデルへ渡し、
訳文のタグを元の要素へ戻す。PLaMo 3 Translate はブラウザ翻訳用にタグを保つ学習をしており、先行事例も 0.8B と 2B でタグの順序の入れ替えまで保たれたと報告している (doc-2)。
タグの数や番号が原文と合わない訳文は、タグを外して翻訳し直す。

#### Markdown (TASK-14)

- 解析は pulldown-cmark (0.13、`default-features = false`) の位置付きのイベントで行い、訳文は原文の翻訳単位の範囲へ差し込む。
  記法 (リストの記号・`>`・表の区切り・コードブロック・HTML ブロック・front matter・リンクの定義) は書き直さずに原文から写すので、入力のまま残る。
- 翻訳単位は 1 つのブロックの中のインラインの並び: 段落・見出し・表のセル・引用の中の段落・リスト項目 (詰めたリストで段落を持たない項目の本文)。
  読む拡張は GitHub の表・取り消し線・タスクリスト・脚注・アラート (`> [!NOTE]`)、front matter (`---` と `+++`)、見出しの属性 (`{#id}`)。
  アラートの印と見出しの属性は翻訳単位に入らない。
- 翻訳単位の文字列は原文に書いたとおりに切り出す (エスケープ `\*` や実体参照 `&amp;` を残す)。引用・リスト項目の続きの行の接頭辞 (`> `・字下げ) は外して渡し、
  訳文の改行のあとに付け直す。接頭辞は 1 行目の始まりから作る (`>` とタブはそのまま、ほかの文字 (`-`・`1.`・`[ ]`) は同じ数の空白)。
  見出しと表のセルの訳文の改行は空白にし、セルではエスケープされていない `|` を `\|` にする。
- 文字 (Unicode の alphabetic) を含まない翻訳単位 (数値だけのセル、URL だけの段落) はモデルへ送らない。
- タグの形:

  | 種類 | 対象 | 渡す形 | 戻し方 |
  |---|---|---|---|
  | 対 | 強調 `em`・強い強調 `strong`・取り消し線 `s`・リンクと画像 `a` | `<em i="1">…</em>` | 中身は訳文、前後は原文の記法 |
  | そのまま | インラインコード・自動リンク (`<https://…>`)・裸の URL `code` | `<code i="2">原文の中身</code>` | 訳文が中に書いたものを捨てて原文 |
  | 空要素 | ハードブレーク `br`、インライン HTML・脚注の参照・中身の無いリンク `x` | `<br i="3"/>` | 原文 |

  番号は翻訳単位の中で 1 から順に振る。そのままの要素にも中身を入れるのは、文の意味をモデルに伝えるためである。
- 訳文のタグは、すべての番号がちょうど 1 回ずつ、原文と同じ名前と種類で現れ、入れ子が交差しないときだけ戻す。順序の入れ替えと入れ子の付け替えは許す。
  戻せない訳文・繰り返した訳文は、まずそのままの要素と空要素のタグだけを残した文字列 (対の要素は中身だけ) で訳し直す。
  インラインコードと URL を、訳文に何が書かれても原文へ戻せるようにするためである (TASK-14 のレビューで指摘を受けて加えた)。
  それも戻せないとき、そのままの要素も空要素も無いとき、1,024 トークンを超えて 1 回では渡せないときは、タグを外した文字列
  (対の要素は中身だけ、そのままの要素と空要素は原文の記法、ハードブレークは改行) で訳し直す (長いときは §7.3 のとおり文の境界で分ける)。
  訳し直すときは直前の対訳を入れない。タグを持つ対訳は、訳文にタグを書くようモデルを促すためである。
- タグを外した訳文に、インラインコードと URL の原文が書いたとおりに (同じ数だけ) 含まれていないときは、その翻訳単位を原文のまま残す
  (2026-11-08 オーナー判断。まれに訳されない段落が残っても、コードと URL を変えないことを優先した)。次の翻訳単位には対訳を入れない。
  1,024 トークンを超える翻訳単位をタグのまま文の境界で分けないのは、対のタグが文をまたぐと分けた部分ごとに戻せなくなるためで、
  そうした翻訳単位もこの確認を通る。
- タグ付きの翻訳単位の訳文は、流れてくる間はタグを隠して訳文欄に出し、終わったら元の記法へ戻した訳文で置き換える。
- 強調は `_` で書かれていても `*` で戻す。`_` は語の中では強調を開かず閉じないので、語の間に空白を置かない日本語の訳文 (`これは_強調_です`) では効かないためである。
- `[label]` と `[label][]` の形のリンクは、訳したラベルでは定義を引けないので `[訳文][label]` の形で戻す。
- 残る制約: 強調の中身が句読点・括弧で始まるか終わり、その外側に空白でも句読点でもない文字が続くと (`これは**「強調」**です`)、CommonMark の規則で強調にならない。
  日本語の訳文で起こりうるが、直すには原文に無い空白を足すことになるので、そのままにした。
- 実測 (TASK-14、M2 の 2B): 英日 (README 風の 19 翻訳単位、うちタグ付き 12) と日英 (13 翻訳単位、うちタグ付き 8) で、
  タグ付きの翻訳単位はすべてタグの数・番号・入れ子が保たれ、タグを外した訳し直しは 0 回だった。語順に合わせたタグの移動
  (`<code i="1">https://…</code> から最新リリースを…`) も保たれた。

### 7.2 形式の判定

- 原文欄の上に形式の選択 (自動 / テキスト / Markdown / JSON / HTML) を置く。
- 自動のときは、JSON として読めれば JSON、`<html` か閉じタグを含むブロック要素が多ければ HTML、見出し・リスト・コードフェンスの記法があれば Markdown、どれでもなければテキストとする。
- 判定した形式を原文欄の上に出す。

### 7.3 長い原文

- 翻訳単位を順に翻訳し、直前の翻訳単位の原文と訳文をプロンプトに入れる (訳語のぶれを抑える)。形は §4.3 の対訳の組。
  1 つの翻訳単位を分けた部分 (下の 2 つ) も、それぞれ 1 つ前の部分の原文と訳文を持つ。
- モデルの学習時の最大長は入力と出力を合わせて 32,768 トークンだが、アプリのコンテキスト長は 8,192 トークン (§4.5)。
  1 回のプロンプトで送る原文は 1,024 トークン (コンテキスト長の 1/8) まで、対訳の組は原文と訳文を合わせて 2,048 トークン (1/4) までとする。
  プロンプトは最大でも約 3,100 トークンで、原文の約 5 倍の長さの訳文を書く余地が残る。対訳の組が 2,048 トークンを超えるときは入れない。
- 1,024 トークンを超える翻訳単位は文の境界で分け、隣り合う文を 1,024 トークンまでまとめ直す。1 文が 1,024 トークンを超えるときは改行で、
  それでも超えるときは同じ文字数ずつに分ける (文の終わりも改行も無い、圧縮された JSON などのため)。
  - 文の終わりは「。！？」(後に続く閉じ括弧・引用符を含む) と、空白の前の「. ! ?」とする。`3.14` や `example.com` は区切らない。
    「はい。」と言った。のように閉じ括弧の後に同じ文が続くときも区切らない。改行だけでは区切らない (英文は文の途中で折り返すため)。
  - トークン数は翻訳エンジンの `/tokenize` で数える。1 トークンは原文の 1 バイト以上に当たるので、バイト数が上限以下の原文は数えずに送る
    (TASK-13 で 2B の GGUF により、英語・日本語・絵文字・サロゲートペアの漢字 (𠮷) などで確認)。
- 出力の末尾が同じ文字列の繰り返しになったら打ち切り (要求の接続を閉じる。§4.3 の停止と同じく、llama-server は生成を取り消す)、
  その翻訳単位を文の単位に分けて訳し直す。1 文しかないときは行に分ける。訳し直した 1 文がまた繰り返したときは、
  繰り返しの 1 回目の終わりまでを訳文として残し、次の翻訳単位には対訳の組を入れない (途中で切れた訳文が次の訳を誤らせないため)。
  - 繰り返しとは、256 文字以内の周期が 3 回以上続き、その長さが 64 文字以上で、かつ原文自身の最も長い繰り返し (罫線など) の 2 倍以上あるものを指す。
    文字単位で調べる。llama-server が送る断片はおおむねトークン単位だが、UTF-8 の文字の途中で終わるトークンは次と合わせて送られ、
    同じ訳文が同じ断片で届くとは限らないためである。
  - 打ち切るまでに訳文欄へ出した訳文は、その翻訳単位の始まりまで取り消してから訳し直す。
- 訳文は、翻訳単位の間の原文の空白 (空行・字下げ) をそのまま挟んで組み立てる。モデルが訳文の前後に付けた空白は落とす。
  1 つの翻訳単位を分けた部分の間は、原文の改行はそのまま残し、改行の無い区切りは訳文の文字で決める。前後とも漢字・かな・全角の記号なら空白なし、
  それ以外は空白 1 つ。日本語の原文には文の間に空白が無いので、原文の区切りをそのまま使うと英訳の文が詰まってつながるためである (TASK-13 で実機で観測)。
- 翻訳中は停止できる。
- 実測 (TASK-13、M2 の 2B): 英語 1,702 トークンの段落 (120 文) は 2 つに分けて 49 秒、日本語 2,482 トークンの段落 (150 文) は 3 つに分けて 71 秒で訳せた。

## 8. 画面

### 8.1 レイアウト

PLaMo 翻訳の画面に倣う。

```
┌ ヘッダー: アプリ名                         [履歴] [設定] ┐
│ [翻訳元の選択欄 ▾]               [翻訳先の選択欄 ▾]       │
│ ┌ 原文 ──── [貼り付け][コピー][クリア] ┐ ┌ 訳文 ──── [コピー] ┐ │
│ │ 複数行入力                         │ │ 読み取り専用        │ │
│ └ 形式: 自動 (Markdown)  判定: 英語 ┘ └────────────────┘ │
│ [⇅]                     [ 翻訳 ] (処理中は「翻訳中…」)      │
└───────────────────────────────────────┘
```

- ウィンドウの幅が狭いときは、原文と訳文を上下に並べる。
- 訳文は翻訳を始めるたびに空にし、ストリーミングで埋める。
- ショートカット: Ctrl/Cmd+Enter で翻訳、Ctrl/Cmd+Shift+C で訳文をコピー。

### 8.2 snz-design の部品との対応

トークンは snz-design のリリース `tokens-v0.1.1` の `snz-tokens.css` を `vendor.mjs copy` で写して使う。写しには手を加えない。

| 画面の要素 | snz-design の部品 |
|---|---|
| 履歴・設定・貼り付け・コピー・クリア・入れ替え | アイコンのみボタン (doc-8 §6.2)。読み上げ用の語を必ず持つ |
| 翻訳元・翻訳先・形式の選択欄 | 入力欄の選択欄 (doc-8 §6.3) |
| 原文と訳文の枠 | パネル (doc-9 §6.3) と複数行入力 (doc-8 §6.3) |
| 翻訳ボタン | ボタンの主操作 (doc-8 §6.1) と処理中の表示 (doc-8 §6.7)。処理中も語を残し、幅を変えない |

### 8.3 配色

- 配色系統 (標準 / Solarized) と明暗の選択 (Light / Dark / OS 追従) の 2 軸を設定画面で選ぶ (snz-design doc-7 §4)。初期値は標準 + OS 追従。
- ヘッダーに明暗の切り替えボタンは置かない。押すたびに保存値が Light / Dark に変わり、OS 追従の選択を消してしまうためである。
- 配色は最初の描画より前に確定させる (doc-7 §7.1)。保存値を `localStorage` に置き、`index.html` の head 内のスクリプトで `data-color-family` と `data-color-mode` を設定する。
  backlog-atlas は Rust から設定を読み終えるまで標準配色を一瞬表示しており、同じ形は採らない。

### 8.4 初版で置かないもの

- 音声入力 (PLaMo 翻訳の画面のマイク)。オフラインで音声を認識するには別のモデルが要り、R6 と相反する。
- 用語集・文脈の入力欄、常体と敬体の選択。モデルは対応しているので、後のフェーズで検討する。

## 9. 翻訳履歴

- 翻訳が完了するたびに SQLite へ保存する。項目は原文・訳文・翻訳元言語・翻訳先言語・形式・モデル名・日時。
- 途中で停止した翻訳は保存しない。
- 原文と訳文を FTS5 で全文検索する。日本語を検索できるように trigram トークナイザーを使う。
- 履歴の一覧から 1 件を選ぶと、原文・訳文・言語の選択を画面へ戻す。
- 保存件数の上限 (既定 1,000 件) を超えたら古いものから消す。全件削除と 1 件削除の操作を持つ。
- 保存先は OS のアプリデータディレクトリ。
